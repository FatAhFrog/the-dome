# 2026-08-28 plans

## Finding: Dome session is bootstrapped four times per Tetris load

Tetris first-paint is slow because of the auth/profile waterfall around the game, not the canvas loop. Gameplay (gravity, input, drawing) is already cheap.

`createBrowserClient` is already a singleton. The waste is four independent “who am I?” bootstraps, not four Supabase apps.

On `/apps/tetris` the same user is fetched separately by:

| Caller | Why it asks | What it then loads |
|---|---|---|
| `middleware.ts` | Gate `/hub` and `/apps` | `getUser()` only (required; server cannot see React state) |
| `BanGuard` | Sign out if banned | `getUser()` + `profiles.is_banned`; **returns `null` until done**, so the board does not paint |
| `ThemeLoader` | Apply theme CSS vars | `getUser()` + `profiles.active_theme` |
| `SidePanel` | News toggle + chat toasts | `getUser()` + `profiles.news_enabled` + rooms + realtime |
| Tetris page | Coins, upgrades, scores | `getUser()` + large `profiles` select + `theme_purchases` |

`getUser()` revalidates with Supabase Auth. Each of those is a full round-trip, then its own `profiles` query.

There is no shared session. `app/(dome)/layout.tsx` mounts `ThemeLoader`, `BanGuard`, and `SidePanel` as siblings that each call `createClient()` and `getUser()`. Tetris does the same after `BanGuard` finally renders children.

### Intended shape

One session owner at the `(dome)` layout; theme / ban / sidebar / pages as children.

- Fetch once on the server in the layout: user + the profile columns those children need.
- Hand that into a small client provider (`DomeSession`).
- Children read `user` / `profile` from context. They keep using the shared client for writes (`earn_coins`, shop, scores).
- Middleware stays as its own server check.
- `BanGuard` must not wrap the tree with `if (checking) return null`. Run the ban check beside the board, not in front of it.

Tetris-only columns (`coins`, upgrades, `theme_purchases`) can stay on the Tetris page if the layout query should stay small. The invariant is: one user, one profile bootstrap, then children.

### Out of scope unless required

- Gameplay / gravity / canvas micro-optimizations (will not move first paint)
- Local Tetris-without-auth route
- Changing shop, coins, scores, or ban behavior

## Finding: Tetris pieces are already cheap; React/network batching is not

Shapes are cell-offset tables, not images. Rotation is `SHAPES[type][0..3]` plus `(x, y)`. Draw is `fillRect` on a 240×480 canvas; next/hold use spawn orientation only. No PNG/atlas, no upload per orientation. Do not add sprite sheets or per-kick bitmaps.

Storing four baked orientations is correct for Tetris. A runtime `rotate(cell)` would not save memory and would fight wall kicks (I/O have special SRS origins).

`createBrowserClient` / session waterfall is still the load-time issue. In-game, “batching” means React and RPCs, not GPU instancing.

This finding is a separate in-game pass. It does not change the first finding’s rule: canvas micro-opts will not move first paint.

### What is not batched well

- Every gravity tick and keypress does `setActive` → full page re-render → `useEffect` → full canvas redraw. No `requestAnimationFrame` loop.
- `lockPiece` fires many `setState`s; `setLevel` inside the `setLines` updater is an extra render.
- Hard drop `setActive(dropped)` then `lockPiece` sets active again.
- `earnCoins(clearedLines)` is already one RPC per clear (good). Do not batch further unless RPC volume over a long session matters.
- Tetris still does its own `getUser` + `profiles` + `theme_purchases` after the layout bootstraps.
- Metrics samples live on the Tetris page. Every second `setMetricsSamples` (up to 7200 rows) re-renders the game and rebuilds four SVG paths.

### Worth doing if this file is touched

- Game state in refs; draw from rAF or only after a move. Score/lines can stay React.
- Metrics timer/samples in a child or ref so the board does not re-render every second.
- `next/dynamic` for `ShopPanel` and `TetrisMetricsPanel`.
- Stop recreating the gravity interval when `lockPiece` identity changes (`nextType` dep).
- Store locked cells as piece type (`'T'`), not baked hex, so theme changes recolor the stack.

### Not worth it

- WebGL, instancing, sprite atlases, offscreen bitmaps per orientation
- Computing rotations instead of the 4-orientation table
- Dirty-rect drawing (~200 `fillRect`s is fine)
- Object-pool `getCells` / stop cloning the 10×20 board

## Implementation (2026-08-28)

Decision boundary: middleware still `getUser()`s (required). After that, `(dome)` owns one cached `getDomeSession()` + `DomeSessionProvider`. Games keep clocks; they do not talk to React every beat. Ban is a server redirect (`signOut` + `/login?banned=1`). Snake stays 120ms grid snaps (no lerp).

### Ownership

- Session (server): [`lib/dome-session.ts`](../lib/dome-session.ts) — `cache(getDomeSession)`; shell columns `is_banned`, `active_theme`, `news_enabled`, `news_category`.
- Session (client): [`components/DomeSession.tsx`](../components/DomeSession.tsx) — only client auth source inside `(dome)`.
- Theme first paint: `themeCssText()` in [`lib/themes.ts`](../lib/themes.ts), injected by [`app/(dome)/layout.tsx`](../app/(dome)/layout.tsx).
- Tetris clock/canvas: [`lib/tetris/useTetrisGame.ts`](../lib/tetris/useTetrisGame.ts) + [`lib/tetris/shapes.ts`](../lib/tetris/shapes.ts). Feature query (coins/upgrades/purchases) stays on the Tetris page.
- Snake clock/canvas: [`app/(dome)/apps/snake/page.tsx`](../app/(dome)/apps/snake/page.tsx) — 120ms snap, `food` not in tick deps, `preventDefault` on arrows.

`BanGuard` is deleted. Layout redirects banned users before paint.
